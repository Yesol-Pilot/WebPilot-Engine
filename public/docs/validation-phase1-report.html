서론 생성형 AI 시대의 3D 품질 보증 패러다임 변화

인공지능(AI) 기술의 비약적인 발전은 텍스트와 2D 이미지를 넘어 3D 콘텐츠 생성 분야에서도 혁명적인 변화를 일으키고 있다. 그러나 대규모 언어 모델(LLM)과 확산 모델(Diffusion Model)을 결합한 생성형 3D 파이프라인은 본질적으로 '환각(Hallucination)'의 위험을 내포하고 있다.

⚠️ 생성 모델의 한계

텍스트 프롬프트의 의미론적 요구사항을 시각적으로 구현하는 데 집중하는 생성 모델은 종종 물리적 법칙이나 3D 렌더링 엔진의 기술적 제약 사항을 간과하는 경향이 있다.

예를 들어, 생성된 가구 모델이 바닥을 뚫고 배치되거나, 벽면과 겹쳐지는 'Interpenetration' 현상, 혹은 렌더링 예산을 초과하는 수백만 개의 폴리곤을 가진 자산이 생성되어 실시간 애플리케이션의 성능을 저하시키는 사례가 빈번하다.

전통적인 3D 제작 파이프라인에서는 숙련된 아티스트와 테크니컬 아티스트(TA)가 수동으로 이러한 오류를 수정했다. 하지만 생성형 AI가 주도하는 자동화된 워크플로우에서는 이러한 인간 개입(Human-in-the-loop)이 병목 구간이 되며, 시스템의 확장성을 저해한다.

✅ 해결책: 자율 검증 에이전트

생성된 결과물의 품질을 즉시 평가하고, 구체적인 수정 피드백을 생성 에이전트에게 전달하여 스스로 문제를 해결하게 만드는 '자율 검증 에이전트(Autonomous Verification Agent)'의 도입이 필수적이다.

본 보고서는 이러한 배경 하에 설계된 검증 에이전트 프로토콜의 Phase 1 구현 전략을 상세히 기술한다.

1 아키텍처 전략: Option A 실행 모델의 타당성 분석

검증 시스템을 설계할 때 가장 먼저 직면하는 결정은 다수의 검증기(Validator)를 어떻게 조직화할 것인가에 대한 문제이다.

🔗
Option A: 순차적 차단
각 검증 단계가 통과되어야만 다음 단계로 진행하는 게이트키퍼 구조 (채택)
⚡
Option B: 병렬 집계
모든 검증기를 병렬로 실행하여 오류를 한 번에 집계

1.1 Fail-Fast 원칙과 자원 효율성

Option A의 가장 큰 강점은 Fail-Fast 원칙에 기반한 자원 관리 효율성이다. 3D 씬 검증 과정에서 PlacementValidator와 PerformanceValidator가 소모하는 연산 비용은 비대칭적이다.

검증 유형 연산 비용 기법
배치 검증 (Placement) 저비용 ⚡ BVH 공간 분할 알고리즘
성능 검증 (Performance) 고비용 🔥 씬 그래프 전체 순회, 재질 파싱

유효하지 않은 씬에 대해 복잡한 렌더링 성능 분석을 수행하는 것은 컴퓨팅 자원의 낭비이다. Option A는 배치 검증을 1차 관문으로 설정하여, 기하학적 오류가 발견되는 즉시 파이프라인을 중단하고 생성 에이전트에게 제어권과 피드백을 반환한다.

1.2 피드백 명확성과 에이전트 혼란 방지

생성 에이전트(Generator Agent) 입장에서 피드백의 질은 수정 성공률과 직결된다. Option B와 같이 복합적인 피드백을 한 번에 전달할 경우, LLM 기반의 에이전트는 우선순위를 설정하는 데 어려움을 겪거나 '퇴행(Regression)'을 범할 가능성이 높다.

💡 Option A의 접근법

한 번에 하나의 명확한 목표를 제시한다. 1단계: "위치만 수정하라", 2단계: "폴리곤 수만 줄이라"는 순차적 지시로 에이전트가 각 문제 해결에 집중할 수 있는 환경을 조성한다.

2 기하학적 정합성 보증: PlacementValidator 상세 설계

PlacementValidator는 3D 공간 내 객체들의 물리적 타당성(Physical Plausibility)을 보증하는 핵심 모듈이다.

💥
충돌(Collision)
서로 다른 객체가 물리적으로 불가능하게 겹치는 교차 현상
🎈
부유(Floating)
중력의 영향을 받는 객체가 공중에 떠 있는 현상

2.1 고속 충돌 감지를 위한 공간 분할 기법 (BVH)

3D 씬에서의 충돌 감지는 계산 복잡도가 매우 높은 작업이다. 가장 단순한 'Brute-force' 방식은 O(N × M)의 연산 복잡도를 가지며, 현대적 3D 환경에서는 실시간 검증이 사실상 불가능하다.

BVH(Bounding Volume Hierarchy)의 원리

  1. AABB(Axis-Aligned Bounding Box): 각 객체나 폴리곤 그룹을 포함하는 최소한의 직육면체 박스를 생성
  2. 계층 구조(Hierarchy): 전체 씬을 감싸는 루트 노드에서 시작하여, 공간을 재귀적으로 분할하며 하위 노드를 생성

이를 통해 충돌 감지의 평균 복잡도를 O(N)에서 O(log N) 수준으로 획기적으로 단축시킬 수 있다.

three-mesh-bvh 활용 및 Shapecast 구현

import { computeBoundsTree, disposeBoundsTree, acceleratedRaycast } from 'three-mesh-bvh';
import * as THREE from 'three';

// 프로토타입 확장
THREE.BufferGeometry.prototype.computeBoundsTree = computeBoundsTree;
THREE.BufferGeometry.prototype.disposeBoundsTree = disposeBoundsTree;
THREE.Mesh.prototype.raycast = acceleratedRaycast;

export function checkCollision(sceneMesh: THREE.Mesh, objectMesh: THREE.Mesh): CollisionResult {
    // 정적 씬의 BVH가 없다면 생성 (캐싱 권장)
    if (!sceneMesh.geometry.boundsTree) {
        sceneMesh.geometry.computeBoundsTree();
    }

    // 객체 자신의 BVH 생성
    if (!objectMesh.geometry.boundsTree) {
        objectMesh.geometry.computeBoundsTree();
    }

    let isColliding = false;
    
    // Shapecast를 통한 볼륨 교차 검사
    sceneMesh.geometry.boundsTree.shapecast({
        intersectsBounds: (box) => {
            return box.intersectsBox(objectMesh.geometry.boundingBox);
        },
        intersectsTriangle: (triangle) => {
            if (objectMesh.geometry.boundsTree.intersectsTriangle(triangle)) {
                isColliding = true;
                return true; // 충돌 확인 시 즉시 중단
            }
            return false;
        }
    });

    return { isColliding };
}
기법 장점 한계
Raycasting 간단한 구현 Deep Penetration 감지 불가
Shapecast 볼륨 기반 정밀 검사, 침투 깊이 측정 상대적 고비용

2.2 부유(Floating) 현상 감지와 레이캐스팅 전략

다지점 샘플링(Multi-point Sampling) 전략

  1. AABB 바닥면 추출: 바닥면의 네 모서리와 중심점 등 최소 5개 이상의 샘플 포인트 선정
  2. 레이 발사: 각 샘플 포인트에서 월드 좌표계의 -Y축(아래쪽) 방향으로 레이 발사
  3. 거리 측정 및 판정:
    • 접촉(Contact): 거리가 허용 오차 ε (예: 0.01m) 이내
    • 부유(Floating): 모든 샘플 포인트에서의 충돌 거리가 ε보다 큼
    • 침투(Penetration): 충돌 지점이 객체의 바닥면보다 위쪽

3 렌더링 효율성 관리: PerformanceValidator 상세 설계

PerformanceValidator는 생성된 씬이 시각적으로 아름다울 뿐만 아니라, 기술적으로 실행 가능한지(Feasible)를 검증하는 역할을 수행한다.

3.1 드로우 콜(Draw Call)과 성능 병목의 상관관계

3D 렌더링 성능을 저하시키는 가장 주된 요인은 GPU의 연산 능력 부족보다는 CPU와 GPU 간의 통신 병목, 즉 드로우 콜(Draw Call)의 과다 발생에 있다.

📊 목표 지표

일반적인 웹 애플리케이션에서 부드러운 60 FPS를 유지하기 위해서는 프레임당 드로우 콜을 100회 ~ 500회 이하로 유지하는 것이 권장된다.

3.2 재질(Material) 속성에 따른 은폐된 비용 분석

특히 MeshPhysicalMaterial의 transmission 속성은 가장 치명적인 성능 저하 요인이다.

조건 추가 비용 이유
기본 드로우 콜 1 기본 렌더링
transmission > 0 +1 투과 패스 추가
roughness 낮음 +가중치 실시간 반사 계산
그림자 캐스팅 +드로우 콜 그림자 맵 생성

정적 성능 예측 알고리즘

interface PerformanceMetrics {
    totalDrawCalls: number;
    totalTriangleCount: number;
    highCostMaterials: number;
}

function analyzeScenePerformance(scene: THREE.Group): PerformanceMetrics {
    let metrics = { totalDrawCalls: 0, totalTriangleCount: 0, highCostMaterials: 0 };

    scene.traverse((object) => {
        if (object instanceof THREE.Mesh) {
            // 1. 드로우 콜 예측
            metrics.totalDrawCalls++;

            // 2. 재질 비용 분석
            if (object.material instanceof THREE.MeshPhysicalMaterial) {
                if (object.material.transmission > 0) {
                    metrics.totalDrawCalls++; // 투과 패스 추가 비용
                    metrics.highCostMaterials++;
                }
            }

            // 3. 폴리곤 수 집계
            const geometry = object.geometry;
            if (geometry) {
                const count = geometry.index 
                    ? geometry.index.count / 3 
                    : geometry.attributes.position.count / 3;
                metrics.totalTriangleCount += count;
            }
        }
    });

    return metrics;
}

4 LangGraph 파이프라인 통합: 상태 주도형 오케스트레이션

PlacementValidator와 PerformanceValidator를 자율적인 에이전트 시스템으로 통합하기 위해 LangGraph 프레임워크를 활용한다.

4.1 상태 스키마(State Schema) 정의

interface AgentState {
    // 생성된 3D 씬 데이터
    sceneData: SceneGraphJSON;
    
    // 현재까지 누적된 검증 오류 목록
    validationErrors: ValidationError[];
    
    // 검증 실패 시 생성된 피드백
    feedbackHistory: string[];
    
    // 무한 루프 방지를 위한 재시도 카운터
    retryCount: number;
    
    // 현재 실행 단계 추적
    currentStage: 'GENERATION' | 'PLACEMENT_CHECK' | 'PERFORMANCE_CHECK' | 'APPROVED' | 'FAILED';
}

interface ValidationError {
    type: 'COLLISION' | 'FLOATING' | 'HIGH_POLY' | 'DRAW_CALL_OVERFLOW';
    objectId: string;
    message: string;
    suggestion?: Vector3; // 예: { x: 0, y: 0.5, z: 0 }
}
